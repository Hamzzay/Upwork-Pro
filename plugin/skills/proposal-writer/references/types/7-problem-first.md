# Type 7. Problem First (Proposal Architecture)

Source: "Stackup Proposal Architecture (Final Version)".

**Chosen when:** the client describes an operational system or workflow problem (inefficiency, manual work, disconnected tools, integration pain) and the job is about how the system will work end to end. Signals in `../type-selection.md`.
**Length:** about 230 to 280 words.

## Structure

1. **Opening line.** "Understood." If the client specifies a starting word, use that instead.
2. **Paragraph 1, problem statement (20 to 30 words).** Show clear understanding of the client's problem: the system complexity, pain points and inefficiencies, using details only this client wrote. Imply confidence in delivering the exact solution.
3. **Paragraph 2, sample work mention (20 to 30 words).** Start with "I've built", never "we". Name two relevant projects aligned with the client's problem.
4. **Paragraph 3, sample work 1 (about 50 words).** Project title, link, then a conversational explanation starting "In [Project], I have built". Connect the implementation directly to the client's requirements.
5. **Paragraph 4, sample work 2 (about 50 words).** Same structure as paragraph 3.
6. **Paragraph 5, approach (45 to 55 words).** The technical and execution approach: tools, APIs, webhooks and workflow structure. Concise and execution focused.
7. **Paragraph 6, call to action (7 to 10 words).** Short, direct and action driven, for example "Let's finalize workflow and start implementation."
8. **Closing.** "Best regards," then the signature from the profile record.

## Project format

```
Project Name – Project Title
[project link]

In [Project], I have built ...
```

Project titles follow the Type 1 title rules (seven to nine words, written fresh, only true details).

## Rules

1. Human, natural tone. No robotic phrasing.
2. Always "I", never "we".
3. Every line aligns with the client's requirement.
4. Show explicitly how the sample work matches the client's needs.
5. No fluff. Concise and valuable.

## Checklist

- [ ] Starts with "Understood." or the client's keyword
- [ ] Problem clearly defined in the client's own details
- [ ] Two relevant sample works included
- [ ] Features clearly matched to requirements
- [ ] Approach within 45 to 55 words, naming tools, APIs, webhooks
- [ ] Tone is human and direct

## Estimates

Apply the estimate answer rule in `../modules.md`.

## Do not

1. Do not follow "Understood." with "your requirements"; the next words must be about their problem.
2. Do not use "we" anywhere.
3. Do not write the approach as a feature list.
