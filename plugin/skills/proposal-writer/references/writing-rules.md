# Writing rules for every type

The chosen type file overrides these rules wherever they differ.

1. **The first two lines are the whole pitch.** They are all the client sees in the list. Use a detail only this client wrote, and say something useful about it. Types 7 and 8 open with their fixed first words ("Understood." or "For your platform,"); the words right after must still be specific to this client.
2. **One insight the client did not already have.** Restating their requirements back to them is not an insight.
3. **Proof is specific.** Types 1, 2, 4, 5, 7 and 8 include two projects in the project format; the second covers a different part of the job. Types 3 and 6 name projects with link lines instead of descriptions. If no genuine second project exists, use one and list it under "Needs your eye".
4. **Plain sentences.** At most three features in one sentence.
5. **Commit to their stack.** Name the tools they named. Never offer "X or Y" when they already chose X.
6. **Answer every explicit ask.** If something cannot be answered honestly, flag it before submitting.
7. **Close on a one line call to action** as the type file describes. No question in the close. Type 8 asks its two questions before the call to action.
8. **Numbers only from the library.** Never estimate or invent a result.
9. **Length fits the type.**
10. **Sign exactly as the profile record says.** Types 7 and 8 put "Best regards," before the signature.

## House style

* Clear, simple English. Short sentences. Always "I", never "we", unless the profile record says otherwise.
* No dashes, except the dash between project name and project title, and in link lines.
* No emojis, no checkmarks.
* No pricing, estimates or timelines unless the client asks; then apply the estimate answer rule in `modules.md`.
* Never mention white label work, such as MD Driven.
* Project facts come only from the project library. Samples in type files illustrate structure; never copy their project claims.
