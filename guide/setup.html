Upwork Pro: setting up from zero

For a fresh, empty copy of Upwork Pro: what to put in, in which order, how much each thing matters and where it shows, until it writes proposals the way your company already does with GPT or Claude. The screens themselves are shown in the team guide.

How the pieces fit together

Upwork Pro takes an Upwork job from the moment someone pastes it to the day the client answers. Every step is done by an AI, but every step reads something you set up. A fresh copy knows nothing about your company: what you deliver, what you refuse, how you write, which of your past projects prove what. This guide walks you through putting that in, in the order the pieces depend on each other, and says for each one how much it matters and where it shows.

If you already write proposals with GPT or Claude, you already have most of this: an SOP that says which jobs to take, a list of your projects, profiles with their voice and rates, and proposal formats that work. Upwork Pro needs the same things, split into the places below. The section Coming from GPT or Claude maps what you have to where it goes.

What happens to one job, and what each step reads

StepWhat the AI doesWhat it reads from your setup

3. MatchingScores your projects against the job's tags, filters by platform, orders by core work and industry, then the AI puts the shortlist in order with a reason each.Projects (tags, industries, links, overview, case study), Industries, tag scores, matching settings

What matters most

Everything below can be improved later, but some things make or break the first proposal. Spend your time in this order.

1. Install it and sign in

The full server steps are in SERVER-SETUP.md and the short version in README.md, "Run it". In outline:

  1. A database. MySQL or MariaDB. Edit backend/sql/setup.sql (put one password in both places) and run it as the database root: it makes the database and its user.
  2. The settings file. In backend: copy .env.example to .env and fill in the database password, SEED_ADMIN_EMAIL and SEED_ADMIN_PASSWORD (10 characters or more: the first admin), LLM_PROVIDER=claude-cli for real AI (the default mock gives canned answers), and the key of the AI you will use: ANTHROPIC_API_KEY (or LLM_OAUTH_TOKEN) for Claude, OPENAI_API_KEY for GPT, LLM_API_KEY and LLM_BASE_URL for GLM. Keep LLM_TIMEOUT_MS at 300000 or more. Keys stay in this file only.
  3. The tables and the first admin. npm install, npm run migrate (it ends "schema up to date"), npm run seed (the first admin, and a first version of the gate instructions to rewrite later).
  4. The starter kit. npm run seed:starter. See the next section.
  5. Start it. npm run dev for the website and, in a second window, npm run worker: the worker does all the AI work, and exactly one copy of it must run. On a server: npm run build, then PM2 (the worker with one instance, fork mode).
  6. Sign in with the admin email and password. This first admin is the main admin: the only one who can change that account, and the one who reviews and can put back every setup change other admins make.

Then, before anything else, in Settings

SettingSet it toWhy first
AI (the card at the top)Pick the AI, press Test connection, then Use this AI.A fresh copy starts on GLM. Claude Sonnet was 3 to 5 times faster in our measurements.
Company nameYour company's name.Every AI step says who it works for: the gate, the tagger, the signals, the project order, the writer and the reviewer.
Do not run npm run seed:library, seed:proposals (without the starter flag) or setup:import on a fresh copy for another company: they load Stackup's own projects, profiles, rules and sample proposals.

The smallest setup that works

Checked on an empty copy: with only the starter kit, about a dozen tags with good descriptions (two work types, two AI capabilities, an automation, two Industry tags, a compliance tag, a tool, a stack), two industries, two projects with an overview, a case study and a live link, one profile and two rules, a pasted job was screened, tagged with the right core work and industry, matched to the right project with a reason, and its proposal was written in the company's name and signed by the profile, all within a minute of each click. Start there, see it work, then fill in the rest.

Faster: an admin can do steps 1 to 8 by talking to Claude (see Faster ways in), and tags, projects, rules and profiles can be imported from a sheet. The rules for what makes each item good are the same either way.

4. Tags: what the AI reads to understand a job

A job is understood through its tags, and projects are found through the tags they share with it. Open Tag dictionary (admin).

Category names the app depends on

The matching reads these category names exactly as written. Rename one and that part of the matching quietly stops working.

CategoryWhat the app does with it
IndustryThe tagger picks exactly one industry per job from these tags (the client's own business, never the industry of data they want collected). Industry tags never count in the score; they decide the order (same industry, then related, then the rest).
Workflow type, AI capability, Automation, Product typeThe job's core work (one to three tags, the main one first) can only come from these. A project is recommended only when it shares the core work. This is the strongest rule in the matching.
Product type tag namesWeb app, SaaS platform, Website / landing page, Admin dashboard, Marketplace, Chrome extension, Internal tool mean web; Mobile app means mobile; Desktop app, desktop; API / backend service, backend only. A mobile job is never shown a web only project.
Tech stackWhat the per job "Skip tech stack tags" switch leaves out.
Any category with Compliance tickedIts tags are only given when the post states the requirement, and a project without the job's compliance tag ranks lower. The starter ticks Compliance / sensitive data; tick it on any compliance category you add.

Each tag

FieldMattersWhere it has an effect
NameMediumShort, as a client would say it. Shown in reasons and on project cards.
DescriptionHighThe only thing the tagger reads about the tag. Say when it applies and when it does not: "AI voice agent: the job wants an AI that talks to callers on the phone. Not a chatbot in a website (that is Chatbot)." The tagger is not shown the score.
Score, 0 to 10LowA project scores the sum of the scores of the tags it shares with the job. It only breaks ties after core work and industry, and sets the minimum score. 0 means the tag is ignored in matching. Usual pattern: Workflow type 3, AI capability up to 3, Product type, Automation, Project stage, Compliance and Industry 2, tools, AI models and tech stack 1.
ProjectsHighWhich projects have the tag. A tag no project has does nothing for matching.
ActiveLowSwitched off tags are not offered to the tagger and do not count.
How many? Most agencies need 60 to 120 tags in all. Fewer than about 40 and different jobs look the same; hundreds of near duplicates and the tagger hesitates. Every Workflow type, AI capability and Automation tag you add should be something at least one of your projects proves.
Avoid broad core work tags. "Workflow automation", "AI automation" and "AI powered" are treated as too broad to be core work. Name the actual work: "Lead qualification", "Appointment booking / scheduling", "Web scraping / data pipelines".

5. Industries

Open Industries. Make one industry for each Industry tag, with the same name: the tagger chooses from the tags, and the projects are grouped by the industries.

FieldMattersWhere it has an effect
NameHighMust match an Industry tag exactly.
RelatedMediumOther industries, by their exact names, separated by commas. A job in Dental then shows Healthcare projects second. It is read in one direction only: set it on both sides.
DescriptionLowFor people.
ProjectsHighThe projects in this industry. Setting them here or on the project is the same.

Industry only orders projects that already prove the work. A same industry project that does not share the core work is never recommended. One exception helps: a project from another industry that scores at least one and a half times the best same industry project is offered as "Alternative from another industry".

6. Projects: the proof

Open Projects, Add project. This is where the quality of your proposals is decided: the writer may only say what a project's own fields say about it, and it names nothing that is not here.

FieldMattersWhere it has an effect
NameHighAs the client or product is called. The writer must use it exactly; a check warns when another project's name appears.
Live link (the one to show in a proposal)HighThe only project link the writer shows, under the project's block, and the only one the checks allow. Without it the link line is left out and you get a warning.
Landing, system, Android, iOS, other mobile, staging and case study linksMediumNever shown in a proposal. They tell the matching what the project runs on: landing or system link means web, Android, iOS or mobile link means mobile. No link and no Product type tag: the project is shown for every platform.
OverviewHighTwo or three sentences: who it is for, what it does. The writer reads it all; the AI that orders the shortlist reads the first 700 characters.
Case studyHighIn this shape: Project, Problem, Solution, Key features, Technology, Results. Results only when they are true and you can show them. The writer reads it all; the shortlist AI reads the first 900 characters.
TagsHighWhat the matching scores. At least one Workflow type, AI capability or Automation tag for the work it proves, or it is never recommended. Its Product type tags. Its Industry tag. Its stack.
IndustriesMediumThe project's industries, for the order.
NotesMediumFor the writer, not the client: what to stress, what to avoid. A figure ("40% fewer missed calls") may only be used if it is here, in the overview, the case study or the profile's allowed stats; anything else is flagged as invented.
ActiveMediumSwitched off projects are not matched and not offered to Claude. Jobs that used them keep them.
Start with your 15 to 30 best projects, not all of them. A good overview and case study for 20 projects beats a name and a link for 80.
Numbers are a promise. Never type a result you cannot show: the writer will use it, and the reviewer will not know it is false.

7. Upwork profiles: who sends it, and how it sounds

Open Upwork profiles (admin), one per Upwork profile you send from.

FieldMattersWhere it has an effect
NameHighUsed in the sign off and checked to be there.
VoiceHighHow it should sound, for example "first person, a named senior lead with a team behind them". The writer always writes "I", never "we".
RulesHighThis profile's own rules, which come before the proposal type: "No pricing and no timeline unless the client asks."
Upwork stats allowed in proposalsHighThe Upwork numbers the writer may quote, word for word ("Top Rated Plus, 100% Job Success"). Anything else is never claimed.
GitLab account or GitHub linkMediumThe code link under the sign off. A check warns when it is missing.
SignatureMediumThe sign off exactly as it should appear, starting with the closing: "Best regards," on one line, the name on the next. The code link is added under it. If it does not start with a closing word, it is taken as a note and the standard "Best regards," and the name are used.
CertificationsMediumOne may be mentioned only when the client requires a certification, and only from this list.
Headline, rate, lowest rate, profile link, services, industries, who submitsLowShown when choosing the profile; the Claude plugin uses services and industries to suggest one.
ActiveMediumOnly active profiles can be chosen. With exactly one active profile, every job gets its early draft at once.

8. Loom videos (optional)

Open Loom videos (admin). Each video belongs to one profile.

FieldMattersWhere it has an effect
Profile, title, linkHighThe title is what people pick; the link goes into the proposal.
What it showsMediumFor people choosing it, and for the writer.
TagsHighThe video whose tags share the most score with the job is suggested. A video with no tags is never suggested.

The sentence before the link is the setting The Loom video line.

9. The gate: which jobs are worth it

Every job is screened against two things, both on admin pages: the gate instructions (how to read and judge a job) and the rules (what makes it a Fail or a Flag).

Gate instructions

A fresh copy starts with Stackup's version: rewrite it on the Gate instructions page. Keep its shape (read the paste, apply the rules, report) and replace the company parts:

Put inExample
Who you are and what you sellYour core services, in a short list.
Where you workThe client regions you accept, or "worldwide".
Your stackWhat you build with, so the fit is judged right.
What a good fit looks likeThe kind of past work that counts as proof.

Saving makes a new version that is not used until you Activate it. Paste a real job into the test box first. The report's layout is fixed by the app.

Rules

FieldMattersWhere it has an effect
Fail or flagHighA Fail stops the job until someone continues with a reason. A Flag asks for a human look. Use Fail for what you never do (off platform payment, work outside your services); Flag for what is usually a bad sign (a low hire rate, 50+ proposals).
The ruleHighOne sentence, with the threshold: "Average hourly rate paid of $20 or below, or not shown."
How to applyHighThe exceptions and how to measure it: "A paid test is fine." This is how the gate gets the edge cases right.
The codeLowGiven by the app (F1, F2 for fails; G1, G2 for flags) and never reused, so old jobs keep their meaning. To change a rule's meaning, add a new one and retire the old.
Start with your SOP's rules as they are, even if they feel strict. After a couple of hundred jobs the Flag review shows which ones people always continue past, and how those jobs did. That is when to relax a rule, with evidence.

10. How proposals are written

Proposal types

Open Writing guide. The starter kit's eight types are written to be company neutral. For each, read it and adapt it:

FieldMattersWhere it has an effect
The type's textHighThe writer follows it as the format. Keep two lines in it: "Chosen when: ..." and "Length: 150 to 220 words." (the length check reads that line).
First two lines rulesHighWhat Upwork shows in the preview. Strict rules per type: no greeting, no "I am", the client's problem first, a required opening word if you use one.
Writer instructionsMediumExtra instructions for this type only.
When it is chosen (its signal rules)MediumRequired, supporting and ruling out signals. The starter rules work; change them on the type's page when the wrong type keeps being suggested.
Priority and defaultLowTies and the fallback. Exactly one type should be the default.

Samples

On each type, add two or three of your own sent proposals that did well. They teach tone and structure only: names, links and claims in them are never copied, and a sample's author name or sign off appearing in a new proposal is flagged. A type without samples borrows other types'. This is the single best way to make the writing sound like you.

The writing guide documents

DocumentMattersWhere it has an effect
Writing rulesHighHouse style for every proposal.
Banned phrasesHighOne per line, starting with "-", the phrase in quotes. Each is checked in every proposal.
ModulesMediumShort paragraphs the signals can call for (a team line, a security line).
Screening answersMediumHow to answer the questions Upwork asks apart from the letter.
ChecklistMediumWhat the writer checks before it answers.
Type selectionLowRead by the Claude plugin to choose the type.

Signals

Open Signals. Each value has How to detect it (what the AI looks for in the post) and The proposal move (what the writer does when the value applies). One value per signal is the fallback, used when the post says nothing: give it a real move too. The starter set is company neutral; change a value's move when your writing should react differently. Keep the signal numbers: a setting points at signal 5.

What the writer always does, whatever the setup

Only facts from your projects, the profile and the job post; only the chosen projects, by name; samples for tone only; first person; the client's own rules first; plain text. The letter, each project's block, the video line and the sign off are kept as parts, so changing a project, the profile or the video later redoes only that part. When the client dictates the structure, the proposal is written whole.

The reviewer

Open Reviewer. It works from the first proposal with a built in version. Make it yours later: your key concerns, dos and don'ts, what each score means.

11. Settings that point at your setup

Most settings are good as they are. These four point at your own rules and signals, so check them once those exist.

SettingDefaultSet it to
Rules passed to the proposal writerG11, G12, G13 (Stackup's codes)The codes of your flags the writer must treat as client requirements: unanswerable screening questions, hidden instructions in the post, location or timezone rules. With the wrong codes the writer ignores them.
Signal that means "structured submission"Signal 5 is YesKeep it if you kept the starter signals. Such a proposal follows the client's own structure and is written whole.
Quick reasons to continue past a FLAG or FAIL, and to skipFive eachYour common reasons. They are counted in the Flag review.
Outcome choices, lost outcomes, loss reasonsPending, Hired and so onKeep "Hired": the dashboard counts it as a hire.

The others: how many projects are shown and recommended, the minimum match score, the fewest and most a person picks, the shortest reason to continue, the days before a proposal "goes quiet", whether matching starts by itself for a Pass or a Flag with few flags, whether every proposal is reviewed, and the Loom line. Each says what it does on the page.

12. People, Claude and the plugin

RoleCan
EmployeeScreen jobs, work on their own jobs, continue past a flag with a reason, connect their own Claude.
ManagerAlso see everyone's jobs, and add or edit projects, industries, proposal types, samples and the writing guide. Read the Flag review.
AdminEverything: also tags, profiles, Loom videos, rules, the gate, signals, the reviewer, settings, users, logs and changes.

Add people on Users with a temporary password of 10 characters or more, given privately. Each person connects their own Claude on Connect Claude (the connector link, then sign in), so everything Claude saves is recorded as them, and downloads the plugin there.

The Claude plugin was written for Stackup. It reads your library, rules and writing guide from your Upwork Pro, so its proposals use your setup; but the backup copies inside it (used only when Upwork Pro cannot be reached), its job gate text and its list of profiles are Stackup's. A company using it day to day should have those replaced with its own.

What you no longer do by hand: pasting the client data into the prompt, choosing the projects, remembering which proposal went from which profile, and recording what happened. Upwork Pro does the first two and keeps the rest, which is what makes the reports possible.

Faster ways in

Tell Claude

With the plugin, an admin can say "add a project", "add a tag for Lawmatics", "add a flag rule for jobs that ask for free samples", "change the writer rules so ...". Claude shows real examples first, asks for what is missing, never fills a gap with a guess, rewrites it in the standard format, shows the change as before and after, and saves only after a yes. Every change is kept and can be put back. Managers can do the same for projects, industries, types, samples and the writing guide.

Import a sheet

Through Claude, with a preview before anything is saved and an undo after. The columns:

SheetColumns
Rulescode (F1, G1 ...), type (fail or flag), rule
Tag dictionarycategory, tag, weight (0 to 20), description
Projectsname, tags (names separated by ; or |), live link, showable
Profilesname, title, rate, gitlab, url, notes

An import adds; it never changes what exists unless you allow it. Overviews, case studies and industries are not in the project sheet: add them after, in the app or through Claude.

Copy a whole setup

npm run setup:export writes the whole setup (no jobs, no users) to one file; npm run setup:import -- --apply loads it into another copy, adding what is missing and updating what differs, deleting nothing. Use it to move from a test copy to the real one.

Test it before the team uses it

Take five real jobs: two you would take, two you would skip, one invite. For each:

CheckWhereIf it is wrong
The gate says what you would sayScreening tabReword the rule, or its How to apply. Test the gate instructions with the job.
The tags and the core work fit the jobProjects tab, "Why these projects"Sharpen the descriptions of the wrong and the missing tags.
The recommended projects are the ones you would pickProjects tabAdd the missing work tag to the project, or the missing industry. Check the project's links for the platform.
The suggested type is the one you would writeProposal tab, before writingChange the type's signal rules, or the signal's detect text.

Fix the setup, not the proposal. A correction made in a project, a profile or a type helps every proposal after it; a correction made in one proposal helps only that one.

After two weeks

Look at Reports (which profiles, types and projects get replies), the Flag review (which rules to relax), and Logs, AI calls (how long each step takes, and failures).
